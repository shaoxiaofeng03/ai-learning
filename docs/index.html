D1 · 读懂第一个服务

目标：看懂 FastAPI 的最小结构，能自己加接口。

四个要点

  2. response_model 决定响应结构和 OpenAPI 文档。
  3. GET 参数用 Query() 校验，POST body 用 BaseModel。

今日任务

自测：参数是一段 500 字文本，用 GET 还是 POST？

POST。GET 参数放 URL，有长度限制，还会被日志和缓存记录。有无副作用决定动词，数据量决定能否用 GET。

D2 · 类型系统与校验

目标：把 Java 的 DTO + Bean Validation 搬到 pydantic。

六个要点

  1. 注解只说明，不校验。Python 的类型标注运行时不检查。
  2. 真正拦截非法输入的是 pydantic，失败自动返回 422。
  3. gt 大于、ge 大于等于、lt 小于、le 小于等于。
  4. 嵌套模型自动递归校验，不用写 @Valid。
  5. 金额用 Decimal，不用 float。
  6. 派生字段（总额）服务端算，用 @computed_field。

类型标注

Stringstr
List<String>list[str]
Map<String,Integer>dict[str, int]
Optional<User>User | None
Set<Long>set[int]

校验对照

Javapydantic

@NotBlankField(min_length=1)

@SizeField(min_length=, max_length=)

自定义 Validator@field_validator

骨架代码

class OrderItem(BaseModel):
    sku: str = Field(min_length=1, max_length=64)
    qty: int = Field(ge=1, le=999)
    price: Decimal = Field(gt=0, max_digits=10, decimal_places=2)

class Order(BaseModel):
    id: str = Field(pattern=r"^ORD-\d{6}$")
    items: list[OrderItem] = Field(min_length=1)

    @computed_field
    @property
    def total(self) -> Decimal:
        return sum((i.qty * i.price for i in self.items), Decimal("0"))

易错点

Field(min_length=1) 拦不住 " "（一个空格）。需要 @field_validator 做 strip 后再判断。

422 的字段路径在 detail[0].loc，嵌套时是 ["body","items",0,"qty"]。

今日任务

自测：def f(x: int) 传 "abc" 会怎样？

什么都不发生，函数里照常拿到字符串。注解只是元数据，运行时不做检查。

自测：为什么金额用 Decimal 不用 float？

float 是二进制浮点，0.1 + 0.2 ≠ 0.3，累计会出分位误差。Decimal 是十进制定点，适合金额。

自测：为什么 total 不让客户端传？

客户端可以传 1 件付 0 元。金额必须服务端根据明细计算，客户端数据不可信。

D3 · 列表推导与生成器

目标：把 Java Stream 的思维翻译成 Python。

五个要点

  1. 列表推导 = filter + map + collect。
  2. 语法：[f(x) for x in xs if cond]。
  3. 生成器 (f(x) for x in xs) 是惰性的，不占内存。
  4. 生成器只能遍历一次，遍历完就空了。
  5. yield 用来写生成器函数，等价于返回 Iterator。

对照

JavaPython
stream().filter(..).map(..).collect()[f(x) for x in xs if cond]
Collectors.groupingBydict 累加 / itertools.groupby
Iterator / 惰性 Stream生成器

代码

nums = [1, -2, 3, -4]
print([x * 2 for x in nums if x > 0])   # [2, 6]

def read_lines(path: str):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.strip()

gen = (x * 2 for x in nums)
print(list(gen))   # [2, -4, 6, -8]
print(list(gen))   # []  第二次就空了

易错点

生成器没有 len()，也不能用下标。需要长度就先 list()——但那就不省内存了。

今日任务

自测：什么时候必须用生成器？

数据量大于内存、只需要顺序处理一次、或者要边读边算（流式）时。比如读大文件、处理日志、分批调用 LLM。

D4 · async / await 的本质

目标：搞清 async 不是多线程，只加速 IO。

五个要点

  1. async def 定义协程，await 让出控制权。
  2. 单线程 + 事件循环 + 协作式调度，不是多线程。
  3. 只适合 IO 密集，CPU 密集不会变快。
  4. asyncio.gather 并发等待多个协程。
  5. 同步函数里不能 await；阻塞调用会卡死整个事件循环。

对照

JavaPython asyncio
线程池事件循环（单线程）
OS 调度，微秒级切换用户态调度，纳秒级
CompletableFuture.allOfasyncio.gather
回调 / thenApplyawait，写法像同步

代码

import asyncio, time

async def work(i: int) -> int:
    await asyncio.sleep(1)
    return i * i

async def main() -> None:
    t = time.perf_counter()
    results = await asyncio.gather(*(work(i) for i in range(10)))
    print(results, round(time.perf_counter() - t, 2))  # ≈ 1.0s

asyncio.run(main())

易错点

在 async 函数里调用 requests.get() 会阻塞整个事件循环，所有协程一起卡住。要用 httpx.AsyncClient。

今日任务

自测：async 能加速 CPU 密集任务吗？

不能。单线程没有并行计算，循环还是循环。CPU 密集要用多进程（ProcessPoolExecutor）或换语言。

D5 · 并发 HTTP

目标：用 httpx + Semaphore 做可控的并发请求。

四个要点

  1. 异步用 httpx.AsyncClient，别用 requests。
  2. Semaphore(n) 限制同时进行的数量，对应 Java 的 Semaphore。
  3. 超时必设，否则一个慢请求拖垮整批。
  4. 一个 Client 复用连接，不要每次新建。

代码

import asyncio, httpx

async def main() -> None:
    sem = asyncio.Semaphore(5)
    async with httpx.AsyncClient(timeout=5.0) as client:
        async def one() -> int:
            async with sem:
                r = await client.get("http://127.0.0.1:8000/health")
                return r.status_code
        codes = await asyncio.gather(*(one() for _ in range(20)))
        print(codes.count(200))   # 20

易错点

不加 Semaphore，20 个请求同时打出去。对方扛不住，或者触发限流，反而更慢。

忘记 async with 关连接，会泄漏连接池。

今日任务

自测：什么场景必须加 Semaphore？

调第三方 API、调 LLM、写数据库时。对方通常有 QPS 限制，或者你的连接池有限。不加就会雪崩。

D6 · 把前五天串起来

目标：写一个小 CLI，同时用到类型标注、pydantic、生成器、asyncio。

题目

读一个本地文本文件，逐行处理，输出出现次数最多的 10 个词。

必须用到的四样东西

  1. 生成器逐行读文件（不要一次 read 全部）
  2. asyncio 并发处理（每条加 await asyncio.sleep(0) 模拟 IO）
  3. pydantic 定义输出模型 WordCount(word, count)
  4. 完整的类型标注

验收标准

  • uv run python week01/day06_cli.py data.txt 能跑
  • 10 万行文件内存占用稳定（不随文件变大而暴涨）
  • 代码 ruff check 无报错

今日任务

自测：为什么统计词频不该用 asyncio.gather 一次收所有行？

10 万行全收进内存就失去生成器的意义了。应该分批（比如每 1000 行一批）并发处理，边处理边累加。
